## Decisions & Rationales

**Why persist refined geometry alongside refined Fopt:**
Per SCALE-004 (docs/findings.md:27), DiffBragg-refined structure factors require matching refined geometry for parity. Prior analysis showed mixing refined MTZ with legacy geometry caused poor metrics. This approach ensures consistency.

**Why maintain fallback to legacy geometry:**
Per input.md pitfall #21, prevent breaking older workflows. The canonical_assets fixture attempts refined first, warns if missing, then falls back to legacy geometry.

**Why update test checksum:**
The manifest checksum changed because refined geometry entries were added to the manifest structure. This is expected and correct—the test assertion was updated to reflect the new canonical baseline.

**Root Cause Analysis:**
- Refined geometry confirmed loaded: `using_refined_geometry: True`, `geometry_source: .../refined.expt`
- Refined MTZ confirmed loaded: `hkl_source: refined_structure_factors.mtz`
- Calibration applied: `spot_scale_override=3.185e17, sqrt=5.643e8`

**Key Observation:**
The canonical golden capture shows high parity correlation (0.807) between DiffBragg and nanobrag_torch simulators (post-refinement, 18 ROIs). However, DB_AT_024 compares zero-iteration forward pass (no refinement) against real detector data (92 ROIs). This suggests:

1. **Hypothesis A:** Zero-iteration forward simulation may legitimately have poor correlation with real detector data even when using refined assets, because the refined geometry was optimized for a different (lower-resolution) image.

**Evidence supporting Hypothesis A:**
- Prior attempt with legacy geometry: corr=0.035 (similar to refined corr=0.019)
- Golden capture is simulator parity, not target alignment
- Zero-iteration vs real data is a harder problem than refined_output vs target
